- **Temps réellement consommé** : bien en dessous. Le mur bloquant a été levé au deuxième

- **Verdict** : **critère de sortie atteint.** Décisions dans les

> les vérifications demandées ensuite — propriété du crate `gpui`, bascule réellement compilée
> et lancée — ont **inversé** la décision vers l'amont Zed. Le §4 et le §6 portent les traces

## 1. Le mur : Xcode complet — et comment il tombe

Établi d'abord, parce que tout en dépendait :

```
$ xcode-select -p                → /Library/Developer/CommandLineTools
$ xcodebuild -version            → requires Xcode, but active developer directory is
                                   a command line tools instance
$ xcrun -f metal                 → unable to find utility "metal"
$ ls -d /Applications/Xcode*.app → aucun
```

Et le build, mesuré plutôt que déduit :

```
cargo::error=metal shader compilation failed:
xcrun: error: unable to find utility "metal", not a developer tool or in PATH
```

**Le prérequis Xcode complet est réel** — le `build.rs` de `gpui` appelle `xcrun -sdk macosx
metal` puis `metallib` pour précompiler `shaders.metal` en `.metallib`.

### Il tombe avec deux drapeaux

En lisant le `build.rs` plutôt qu'en cherchant à installer Xcode :

```rust
#[cfg(feature = "runtime_shaders")]      → assemble les shaders, compilation au LANCEMENT
#[cfg(not(feature = "runtime_shaders"))] → compile_metal_shaders(...)   ← le mur
```

Un second chemin existe aussi, `macos-blade`, qui remplace le renderer Metal par
`blade-graphics`. Non exploré : `runtime_shaders` est le plus petit changement et garde le
renderer standard.

**Piège mesuré** : activer `runtime_shaders` sur `gpui` seul ne suffit pas. Le mur se déplace
sur `gpui_macos`, tiré par `gpui_platform`, qui a **son propre** `build.rs` et sa propre
feature. Il faut les deux :

```toml
gpui = { package = "gpui-ce", version = "0.3.3", default-features = false,
         features = ["font-kit", "runtime_shaders"] }
gpui_platform = { git = "https://github.com/gpui-ce/gpui-ce", default-features = false,
                  features = ["font-kit", "runtime_shaders"] }
```

Avec ça : `Finished dev profile`. **Aucun Xcode.**

`default-features = false` en prime : les defaults tirent `wayland` et `x11`, inutiles sur une
cible macOS uniquement.

**Contrepartie non mesurée** : les shaders sont désormais compilés **au démarrage** de l'app.
Le coût est déplacé, pas supprimé. À chiffrer avant de le déclarer négligeable.

## 2. Le point technique central : un `Receiver` tokio dans une vue gpui

C'est la question dont tout le reste découlait. La réponse tient en deux faits.

**gpui garde le thread principal** — sur macOS l'AppKit run loop y vit, ce n'est pas
négociable. Le daemon vit donc dans **son** runtime tokio, sur **son** thread :

```rust
let (observer, observations) = observe_channel();
std::thread::spawn(move || {
    tokio::runtime::Runtime::new().expect("runtime").block_on(alimente(observer));
});
Application::new().run(move |cx| { /* gpui a le thread principal */ });
```

**Un `tokio::sync::mpsc::Receiver` s'attend depuis l'exécuteur de gpui, sans runtime tokio
courant.** Le canal n'a besoin ni du réacteur I/O ni des timers — seulement d'un waker. Donc :

```rust
cx.new(|cx| {
    let mut observations = observations;
    cx.spawn(async move |this, cx| {
        while let Some(observation) = observations.recv().await {
            if this.update(cx, |flux: &mut Flux, cx| {
                flux.pousser(observation);
                flux.defilement.scroll_to_bottom();   // suivre la queue
                cx.notify();                          // redessiner
            }).is_err() {
                break;                                // la fenetre est fermee
            }
        }
    })
    .detach();
    Flux::new()
})
```

**Compilé du premier coup**, et le comportement est celui attendu. Trois points de détail qui
comptent :

- `this.update(...)` rend un `Result` : il échoue quand l'entité a disparu. C'est le signal de
  fermeture propre, pas une erreur à ignorer.
- `cx.notify()` est ce qui déclenche le rendu. Sans lui l'état change et l'écran ne bouge pas.
- Le `Task` doit être `.detach()` ou gardé : abandonné, il est annulé.

**Ce que ça implique pour l'app** : aucune passerelle, aucun pont, aucune sérialisation. Le
même `Receiver<Observation>` que consomme la TUI alimente la GUI. L'[ADR 0022](../adr/0022-decoupage-daemon-gui.md)
en fait la règle.

## 3. Le critère de sortie : la liste défile

Trois captures d'écran, relues — pas déduites.

**Premier rendu.** La fenêtre s'ouvre, `87 observations recues`, le scénario canonique lisible
avec ses couleurs :

```
  session ajout-handlers — transport aucun          (bleu)
  session refacto-api — transport aucun             (bleu)
  ecrit    auth.rs                                  (gris)
  lu       auth.rs                                  (gris)
  ecrit    auth.rs                                  (gris)
▲ ECRIT    handlers.rs  perime : auth.rs (par refacto-api)     (jaune, marqueur)
~ observe  notes.txt  hors-bande, sans verdict                 (magenta, marqueur)
  lu       src/module_00.rs …                       (gris)
```

Le contenu **débordait** — mais déborder n'est pas défiler. Un `ScrollHandle` suivi par
`div().track_scroll(&handle)` plus `scroll_to_bottom()` à chaque observation :

**Deuxième capture** — la vue montre `module_56` à `module_79` : la queue, pas la tête.
L'offset a bougé.

**Troisième capture** — bandeau fixe hors du conteneur défilant, et l'offset devient
observable : `sonde gpui-ce — 87 observations recues · offset -1342 px`, tail à `module_79`.

Un détail trouvé par la capture et pas par la relecture : dans la première version le bandeau
était **dans** le conteneur défilant, donc il disparaissait avec le défilement. Une en-tête qui
défile n'est pas une en-tête. `flex_col` + `flex_none` pour le bandeau, `flex_1` +
`overflow_y_scroll` pour la liste.

`87` est exactement le nombre émis : 2 sessions + 5 lignes de scénario + 80 lectures. Aucune
observation perdue.

## 4. `gpui-component` : tranché par la compatibilité

```
gpui-component 0.5.1  →  depend de  gpui 0.2.2
                          (crates.io, repository declare : zed-industries/zed)
```

`gpui` 0.2.2 et `gpui-ce` 0.3.3 sont **deux crates distincts**. Les mettre ensemble met deux
frameworks dans le graphe : deux `App`, deux `Window`, aucune conversion. La compilation
échoue, et elle échouerait même en réglant les shaders.

**Donc inutilisable avec notre épinglage**, et la question de l'utilité ne se pose pas. Si elle
se posait : le périmètre v0.1 tient avec `div`, du texte, `rgb()` et un `ScrollHandle`. Une
bibliothèque de composants ajouterait un **second amont à suivre** pour des boutons dont on
n'a pas besoin.

## 5. Coût de mise en place, réel

| | |
|---|---|
| Xcode complet | **non requis**, grâce à `runtime_shaders` |
| Dépendances résolues | 706 paquets pour `gpui-ce` + `gpui_platform` |
| Compilation à froid | quelques minutes, dominées par `gpui-ce` lui-même |
| Compilation incrémentale de la sonde | ~2–5 s |
| Lignes de la sonde | ~230, dont ~60 de rendu |

Le coût dominant n'est pas la mise en place, c'est le poids du graphe de dépendances.

## 6. Ce qui n'a pas été établi

À dire explicitement plutôt qu'à laisser supposer :

- **L'échappatoire vers l'amont Zed n'est pas mesurée** (ADR 0023). Elle repose sur la
  propriété drop-in annoncée. À vérifier avant d'en dépendre.
- **Le temps de démarrage** avec compilation des shaders au lancement.
- **Le comportement sans cache de compilation**, sur une machine neuve.
- **Signature et notarisation** d'une app gpui, exigées pour distribuer.
- **Le défilement à la molette** n'a pas été testé — je n'ai pas de moyen de synthétiser un
  geste de scroll ici. Ce qui est prouvé est le contrôle **programmatique** de l'offset, qui
  est ce dont un flux vivant a besoin. La molette reste à constater de visu.
- **Aucun canari** sur cette dépendance, contrairement à l'adaptateur ACP. Assumé : une
  rupture `gpui` casse le build, bruyamment.

## 7. Reproduire

La sonde vit **hors du dépôt**, dans `/tmp/sonde-gpui`, à dessein : l'[ADR 0022](../adr/0022-decoupage-daemon-gui.md)
devait être écrite avant que du code gpui entre dans le workspace. Son `Cargo.toml` est celui
de la section 1, plus les crates du produit en dépendances de chemin — `trame-daemon`,
`trame-registry`, `trame-journal`, `trame-core` — parce que **rien n'est simulé** : les
observations viennent du vrai registre, et les verdicts sont ceux qu'il rend.

```sh
cargo run                          # la fenetre s'ouvre
screencapture -x /tmp/shot.png     # et on relit l'ecran
```
